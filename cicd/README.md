# PredML CI/CD

## Jenkins agent image

[`Dockerfile.jenkins-agent`](./Dockerfile.jenkins-agent) builds the reusable
`predml-ci` Jenkins agent image with Java, Git, Docker CLI, AWS CLI, and
Terraform.

Run these commands from **Ubuntu WSL**. Do not run the Linux commands below
directly in Windows PowerShell.

### Open Ubuntu WSL from Windows

From the Windows Start menu, open **Ubuntu**, or run this from PowerShell:

```powershell
wsl -d Ubuntu
```

If Ubuntu is not installed, list available distributions:

```powershell
wsl --list --online
```

Install Ubuntu from an elevated PowerShell, if required:

```powershell
wsl --install -d Ubuntu
```

Restart Windows if prompted, then open Ubuntu and create the Linux username and
password requested by WSL. These are separate from the Jenkins web username and
password.

Inside Ubuntu WSL, move to this repository:

```bash
cd /mnt/e/Projects/mlops-genai-project
pwd
```

The `/mnt/e/...` path is the WSL equivalent of the Windows path
`E:\Projects\mlops-genai-project`. Keep your existing files, virtual
environments, and project data; do not delete the repository to set up Jenkins.

### Check Docker from Ubuntu WSL

This project can use a Docker Engine installed directly inside Ubuntu WSL; it
does not require Docker Desktop. Start the Docker service from Ubuntu if it is
not already running:

```bash
sudo service docker start
docker context show
docker info
docker --version
```

The context should normally be `default`, and `docker info` should show server
information. The Docker socket used by the Jenkins agent should also exist:

```bash
test -S /var/run/docker.sock && echo "Docker socket is available"
```

If `sudo service docker start` reports that Docker is not installed, install
Docker Engine in Ubuntu WSL using Docker's official Ubuntu instructions. Do
not install Docker Desktop or enable Docker Desktop WSL integration if you are
using this native WSL Docker Engine workflow.

If `docker images` lists `predml-ci:1.0` and `docker info` succeeds, the image
is already available to this Docker daemon and you can skip the build step.

### Build the Jenkins agent image

Run this from the repository directory in Ubuntu WSL:

```bash
docker build \
  --tag predml-ci:1.0 \
  --file cicd/Dockerfile.jenkins-agent .
```

The Docker daemon must be running in WSL. Verify it with:

```bash
docker info
```

## Verify the image tools

The image's default entrypoint starts the Jenkins inbound agent. Use
`--entrypoint` when testing an individual tool:

```bash
docker run --rm \
  --entrypoint terraform \
  predml-ci:1.0 version

docker run --rm \
  --entrypoint aws \
  predml-ci:1.0 --version

docker run --rm \
  --entrypoint docker \
  predml-ci:1.0 --version

docker run --rm \
  --entrypoint git \
  predml-ci:1.0 --version

docker run --rm \
  --entrypoint java \
  predml-ci:1.0 -version
```

To inspect all tools in one interactive shell:

```bash
docker run --rm --interactive --tty \
  --entrypoint /bin/bash \
  predml-ci:1.0
```

Then run:

```bash
terraform version
aws --version
docker --version
git --version
java -version
exit
```

## Docker socket mount

The `-v` option mounts the WSL Docker socket into the Jenkins agent
container. It gives the container's Docker CLI access to the Docker daemon
running in WSL:

```bash
-v /var/run/docker.sock:/var/run/docker.sock
```

This is not a standalone shell command and it is not a PowerShell command.
Use it as part of `docker run` from Ubuntu WSL when launching the image as a
Jenkins agent. It is not needed when checking Terraform, AWS CLI, or Git:

```bash
DOCKER_SOCK_GID=$(stat -c '%g' /var/run/docker.sock)

docker run --detach \
  --name predml-ci-agent \
  --network host \
  --group-add "$DOCKER_SOCK_GID" \
  --volume /var/run/docker.sock:/var/run/docker.sock \
  predml-ci:1.0 \
  -url http://172.31.176.1:8081 \
  -webSocket \
  -secret "<agent-secret>" \
  -name "predml-ci-agent"
```

Replace `<agent-secret>` with the secret generated by Jenkins for the
configured inbound agent. Do not commit the secret or put it in a Dockerfile,
Jenkinsfile, or shell history.

### Create and start the Jenkins agent

The Jenkins controller should already be running on Windows at
`http://localhost:8081`.

1. In Jenkins, go to **Manage Jenkins > Nodes > New Node**.
2. Create a permanent node named `predml-ci-agent`.
3. Set its label to `predml-ci`.
4. Select **Launch agent by connecting it to the controller**, save, and copy
   the generated launch command or secret. Jenkins generates the secret; you
   do not create one manually. If no secret or command is shown, open the
   `predml-ci-agent` node page after saving and select **Launch agent** or
   **Relaunch agent**. Confirm that the launch method is
   **Launch agent by connecting it to the controller**.
5. In Ubuntu WSL, run the `docker run` command above, replacing
   `<agent-secret>` with the secret from Jenkins. Keep the secret private.

Check that the agent is connected:

```bash
docker ps
docker logs --tail=100 predml-ci-agent
docker exec predml-ci-agent docker version
```

The `--group-add` option gives the container's `jenkins` user the numeric group
permission required by the mounted Docker socket. Without it, the agent can
connect to Jenkins but Jenkins jobs cannot run Docker commands.

The agent is ready when its logs include both:

```text
INFO: WebSocket connection open
INFO: Connected
```

Also confirm that `predml-ci-agent` is **Online** at
`http://localhost:8081/computer/`. A running container alone does not prove
that the agent connected to Jenkins.

The agent container uses the host Docker socket. This gives Jenkins jobs
significant control over Docker, so only use it on a trusted local machine and
do not expose Jenkins port 8081 to an untrusted network.

### Cold-start order after a laptop restart

Use this order whenever Windows or the laptop has been restarted:

1. Confirm that the Jenkins Windows service is running from elevated
   PowerShell:

   ```powershell
   Get-Service Jenkins
   Start-Service Jenkins
   ```

   `Start-Service` reports that the service is already running if no action is
   needed.
2. Open Ubuntu WSL from PowerShell or the Start menu:

   ```powershell
   wsl -d Ubuntu
   ```
3. Start the native WSL Docker Engine and verify it:

   ```bash
   sudo service docker start
   docker info
   ```
4. Start the existing Jenkins agent container:

   ```bash
   docker start predml-ci-agent
   docker logs --tail=100 predml-ci-agent
   docker exec predml-ci-agent docker version
   ```

   To start the agent later without recreating the container, use:

   ```bash
   docker start predml-ci-agent
   docker logs --tail=100 predml-ci-agent
   ```
5. Confirm the logs contain `WebSocket connection open` and `Connected`, then
   confirm `predml-ci-agent` is **Online** at
   `http://localhost:8081/computer/`.

The `predml-ci:1.0` image and the stopped `predml-ci-agent` container persist
across restarts, so rebuilding the image is not normally required. If the
container was deleted, recreate it with the `docker run` command above. If the
WSL gateway address changed, update the agent URL before recreating it.

### Restart the agent after shutdown

Shutting down or restarting the laptop stops the Jenkins Windows service,
Ubuntu WSL, and the agent container. The container and the `predml-ci:1.0`
image remain stored, but the container does not automatically reconnect unless
you configure a separate startup service.

After starting Windows Jenkins and Ubuntu WSL again, run:

```bash
sudo service docker start

docker start predml-ci-agent
docker logs --tail=100 predml-ci-agent
```

If the container was removed, recreate it with the `docker run` command above.
If the existing container was created without `--group-add`, remove and
recreate it so the permission is applied:

```bash
docker rm --force predml-ci-agent
```

If the WSL gateway address changes after a restart, find the current address
and update the agent URL:

```bash
ip route | awk '/default/ {print $3; exit}'
```

The Jenkins controller must be running before the agent can reconnect.

If an old agent container already exists, stop and remove only that named
container before starting it again:

```bash
docker stop predml-ci-agent
docker rm predml-ci-agent
```

Do not remove the Jenkins Windows service, the Jenkins home directory, or
unrelated Docker volumes as part of this setup. Those may contain your Jenkins
jobs, credentials, plugins, or other project data.

The exact `-url`, `-secret`, and `-name` values come from the Jenkins inbound
agent configuration. The Jenkins node should have the label:

```text
predml-ci
```

The pipelines use `agent any`, so they run on the built-in Windows node by
default when no other online executor is available. Because the pipeline uses
Windows `bat` steps, keep the old Linux `predml-ci` node offline or configure
the jobs so they can run only on the Windows built-in node. The Windows
Jenkins service account must be able to resolve `aws`, `docker`, and
`terraform` from its `PATH`.

The old Linux agent setup is optional and is not required for these pipelines.
If a label is used in a custom pipeline, configure it separately:

```groovy
agent {
    label 'predml-ci'
}
```

## Jenkins pipelines

- [`Jenkinsfile-batch`](./Jenkinsfile-batch): builds and pushes the batch image,
  builds and pushes the realtime API image to the API ECR repository, and
  starts the SageMaker training pipeline.
- [`Jenkinsfile.terraform`](./Jenkinsfile.terraform): validates, plans,
  applies, or destroys Terraform infrastructure.

### Jenkins pipeline setup

Use this order for the first deployment:

1. Confirm the Jenkins built-in Windows node has an executor available.
2. Run the Terraform pipeline with `TF_ACTION=plan`.
3. Review the plan and confirm the AWS account and resources.
4. Run the Terraform pipeline with `TF_ACTION=apply`.
5. Approve the Jenkins approval prompt.
6. Verify the AWS resources and Terraform outputs.
7. Run the batch pipeline.

Do not run `destroy` unless you intentionally want to remove the managed
infrastructure.

The AWS batch image uses the cloud-specific implementation under
`PredML/AWS/src`; the local implementation under `PredML/src` is not modified
or packaged into that image. AWS stages read and write S3 through the
`S3_BUCKET` and optional `S3_PREFIX` environment variables. The MLflow tracking
URI must be supplied with `MLFLOW_TRACKING_URI` (or
`SAGEMAKER_MLFLOW_TRACKING_URI`) when running a training or registry stage.
Changes to `PredML/AWS/src` or `PredML/docker/batch.Dockerfile` rebuild and push
the AWS image.

The AWS image does not generate seed data. Upload the raw input file to the
Terraform-created `input/` prefix:
`s3://<bucket>/<prefix>/input/raw_data.csv` before running stage
`01_preprocess`. AWS stages use the Terraform-created `processed/`,
`features/`, `models/`, `output/`, `monitoring/`, and `mlflow-artifacts/`
prefixes. The AWS implementation keeps
`mlflow_registry.py` because the SageMaker MLflow Tracking Server currently
provides model registration, aliases, and promotion; it can be replaced later
when SageMaker Model Registry is adopted.

#### Connect Jenkins to GitHub

For a private repository, create a GitHub fine-grained personal access token
with access limited to this repository and **Contents: Read-only** permission.
Do not use your GitHub password.

In Jenkins, go to **Manage Jenkins > Credentials > System > Global credentials
(unrestricted) > Add Credentials** and create:

```text
Kind: Username with password
Username: your GitHub username
Password: GitHub personal access token
ID: github-repository-read
```

For a public repository, Git credentials are normally not required. Never
commit GitHub tokens, AWS keys, or Jenkins agent secrets.

#### Create the Terraform pipeline job

1. Select **New Item**.
2. Enter `predml-terraform-pipeline`.
3. Select **Pipeline** and click **OK**.
4. In the **Pipeline** section, select **Pipeline script from SCM**.
5. Select **Git** as the SCM.
6. Set the repository URL:

   ```text
   https://github.com/aswamca/mlops-genai-project.git
   ```

7. Select the GitHub credential if the repository is private.
8. Set the branch specifier to:

   ```text
   */main
   ```

9. Set the script path to:

   ```text
   cicd/Jenkinsfile.terraform
   ```

10. Save the job.

Select **Build with Parameters**, choose `plan`, and start the build. The
pipeline checks AWS access, prepares the encrypted/versioned Terraform state
bucket, initializes the local modules under `PredML/AWS/terraform/modules`,
validates the configuration, and archives the Terraform plan.

After reviewing a successful plan, run **Build with Parameters** again with
`TF_ACTION=apply`. Approve the prompt only after confirming the intended AWS
account and resources.

The Terraform pipeline expects these Jenkins credential IDs:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

It sets the S3 bucket name and AWS region from the pipeline environment. The
remote state bucket is `predml-terraform-state-ap-southeast-2` and the state
key is `predml/terraform.tfstate`.

#### Create the batch pipeline job

After Terraform succeeds:

1. Select **New Item**.
2. Enter `predml-batch-pipeline`.
3. Select **Pipeline** and click **OK**.
4. Select **Pipeline script from SCM**.
5. Select **Git**.
6. Use the same repository URL, branch, and GitHub credential as the Terraform
   job.
7. Set the script path to:

   ```text
   cicd/Jenkinsfile-batch
   ```

8. Save the job and select **Build Now**.

The batch pipeline expects these Jenkins credential IDs:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
AWS_ACCOUNT_ID
```

It builds and pushes the `predml-batch` image to ECR when one of the files
copied by the batch Dockerfile changes: AWS source stages `01` through `06`,
`08` through `10`, AWS configuration/MLflow files, the AWS requirements file,
or the batch Dockerfile. It builds and pushes the realtime API image to
`predml-api` when the API Dockerfile, API requirements, or one of the API
source files copied by the API Dockerfile (`config.py`,
`mlflow_registry.py`, `07_realtime_inference.py`, or `09_forecast.py`)
changes. Batch changes also start the configured SageMaker training pipeline.

After the job finishes, its `post` cleanup removes the Jenkins-created
`predml-batch:latest` and `predml-api:latest` tags, the temporary
ECR-qualified tags, logs out of ECR, and deletes the Jenkins workspace. It does
not remove local development images such as `predml-local/api:latest`,
`predml-local/batch:latest`, or `predml-local/mlflow:latest`. The pushed images
remain in ECR.

#### Triggering builds

Use manual **Build with Parameters** or **Build Now** for the first runs.
GitHub cannot normally send a webhook to `http://localhost:8081`; a webhook
requires a secure, reachable HTTPS endpoint. SCM polling can be configured
later if required, but manual runs are recommended until the pipelines have
been verified.

Both Jenkinsfiles use the Jenkins built-in Windows node with:

```groovy
agent any
```

## Jenkins web login recovery

The Jenkins web username/password and the inbound agent secret are different:

- Jenkins web login: used at `http://localhost:8080`
- Inbound agent secret: used only by the agent container command
- AWS credentials: stored separately in Jenkins Credentials

Do not disable Jenkins authentication as a normal solution. An unauthenticated
Jenkins controller can allow anyone who can reach port 8080 to execute jobs,
read secrets, or control the machine.

If Jenkins was just installed and the setup wizard has not been completed,
retrieve the initial administrator password in PowerShell:

```powershell
Get-Content "C:\ProgramData\Jenkins\.jenkins\secrets\initialAdminPassword"
```

If the Jenkins home directory is different, inspect the Windows service:

```powershell
Get-CimInstance Win32_Service -Filter "Name='Jenkins'" |
    Select-Object Name, PathName
```

If you can log in with another administrator account, reset the password from
**Manage Jenkins** > **Users** > select the user > **Configure**.

If there is no working administrator account, stop the Jenkins Windows service
before performing a local recovery procedure:

```powershell
Stop-Service Jenkins
```

Back up the Jenkins `config.xml` and `users` directory before changing any
files. After recovery, restore authentication immediately and start Jenkins:

```powershell
Start-Service Jenkins
```

Do not delete the Jenkins user database or edit security settings without a
backup. If you are unsure which Jenkins home directory or account is in use,
confirm it before changing files.
